# Phase 6b live run: workload identity (November 2026)

SPIRE 1.15.5 on the same Windows 11 machine, Docker Desktop. SPIRE's images
couldn't be pulled where it was built, so this was its first run anywhere; the
configs had been checked against SPIRE's documentation and source, and the
ledger and callers tested against a stand-in agent speaking the real Workload
API. It worked on the first run. Everything below is copied from PowerShell
and the console.

## SPIRE starts and recognises containers

With `LEDGER_AUTH=keys` (nothing switched yet), `spire-server` and
`spire-agent` came up healthy. The agent log:

```
SVID is not found. Starting node attestation
Node attestation was successful  reattestable=false
  spiffe_id="spiffe://warden.local/spire/agent/join_token/751602fa-…"
Starting agent APIs  address=/run/spire/sockets/agent.sock
Creating X509-SVID  entry_id=warden-backend  spiffe_id="spiffe://warden.local/backend"
Creating X509-SVID  entry_id=warden-policy   spiffe_id="spiffe://warden.local/policy"
Creating X509-SVID  entry_id=warden-ledger   spiffe_id="spiffe://warden.local/ledger"
```

Asked from inside the backend container:

```
spiffe://warden.local/backend 1793677968
```

The docker workload attestor found the calling process's container inside
Docker Desktop's VM (cgroup v2, `pid: host`) and matched its Compose labels.
This was the step most likely to fail on a new machine.

## Switching the ledger to identities

`LEDGER_AUTH=spiffe` in `.env`, then the backend, policy and ledger recreated.

| Check | Result |
| --- | --- |
| `printenv LEDGER_AUTH` in ledger and backend | `spiffe`, `spiffe` |
| The real `LEDGER_WRITE_KEY`, sent from the backend container | `401 {'detail': 'the ledger takes writes from workload identities only'}` |
| The policy service's own SPIRE identity, attempting a write | `403 {'detail': 'spiffe://warden.local/policy may not write the ledger'}` |
| Invoice `K-2026-007` (MYR 12.00), approved by Rajesh | **Paid**, transaction 47 |

The write key is still in the backend's environment and in `.env`, and it
moves nothing: writes need an identity SPIRE gives only to the backend
container. The policy service holds a genuine identity, and it can read but
not write.

## The write key removed (PR #35)

With identities proven, `LEDGER_WRITE_KEY` was deleted from Compose,
`.env.example`, `fill-secrets.py` and the machine's `.env`. `VENDOR_LOOKUP_KEY`
stays only with the ledger and the console, which reads with it.
`LEDGER_AUTH=spiffe` is the Compose default; the backend, policy and ledger
wait for the SPIRE agent.

Invoice `K-2026-008` (MYR 9.00), approved by Amira: **Paid**, transaction 49,
with no write key anywhere on the machine.

## Findings

1. **SPIRE's docker attestor works on Docker Desktop** with `pid: host` and the
   Docker socket mounted read-only into the agent; no cgroup settings needed.
2. **The approval agent escalated low-risk invoices three times running**:
   `K-2026-007` (risk 0.10, six settled payments, "escalate, 88% sure") and
   `K-2026-008` (risk 0.20, seven settled payments, "escalate, 91% sure"). Escalation stands on one answer;
   the phase 9b consistency check had shown this agent leaning that way. Safe,
   but it sends invoices to people that the rules would let through; worth
   tracking on the dashboard's escalation panel (`approval_agent`).
3. **The write key is gone** (above). The secrets left in `.env` are the model
   providers' API keys, the database passwords and the console's read key;
   a vault for those is phase 6b part 2, or Azure Key Vault in phase 11.
