# Fixes after phase 11, measured live (November 2026)

Three findings from the phase 11 runs were fixed in one change: totals that
include tax, names written in capitals, and the approval agent's criteria. They
were checked on the same Azure deployment, before and after
`.\infra\azure\deploy.ps1`. Everything below is copied from PowerShell and the
console.

## The approval agent: measured, not guessed

The approval prompt was rewritten with concrete conditions. Auto-approve when
the risk is low, the amount is in line with the vendor's history, the remit-to
account matches, and the fields are complete and add up. Escalate only for a
concern that points at the evidence. Escalating routine invoices is named as a
failure too. The agent is also told which rules code already enforces (the
routine amount limit, among them), so it doesn't escalate for those.

To measure the change, a routine invoice from Kestrel (3 settled payments,
average 347.33) went through the old prompt first:

| | |
| --- | --- |
| Invoice | K-2026-201, MYR 274.00, two lines, no tax |
| Risk | low (0.22) |
| Approval | auto approve, 95% sure (asked 3 times, all agreed) |
| Outcome | paid, transaction 9 |

Then the phase 9b consistency tool asked the risk and approval agents about
that **same run** 5 times, before the deploy (revision 11, old prompt) and after
(revision 12, new prompt). It sends the same evidence each time, so the only
difference is the prompt:

```
az containerapp exec -n warden-backend -g warden-rg --command "python -m app.consistency b2cb2ae4-8a1f-44f9-a2dd-56430c909257 --times 5"
```

| | Before (old prompt) | After (new prompt) |
| --- | --- | --- |
| Approval decisions | 5 of 5 auto_approve (15 of 15 asks) | 5 of 5 auto_approve (15 of 15 asks) |
| Approval confidence | 0.90, 0.95, 0.95, 0.97, 0.95 | 0.98, 0.98, 0.98, 0.98, 0.97 |
| Risk scores | 0.25, 0.25, 0.25, 0.25, **0.35 (medium)** | 0.25, 0.25, 0.25, 0.20, 0.25 |
| Risk spread | 0.10 | 0.05 |

The new prompt makes the same decision, more surely and more evenly: its
confidence ranges over 0.01 where the old prompt's ranged over 0.07. The routine
invoice was already paid without a person, so this run can't show fewer
needless escalations. It does show that the stricter wording ("escalate only
for a named concern") didn't make the agent more nervous about a clean invoice.

**One thing to watch.** In the "before" asks the risk agent once scored the
same invoice 0.35, "medium", at temperature 0. That came from the model, not the
evidence. The new approval prompt says to escalate on medium risk, so a single
medium score in a live run would send a routine invoice to a person. The
unanimity rule (3 of 3 approval asks) doesn't cover it, because the risk score
is computed once per run. The "after" asks gave five low scores; the workbook's
"Consistency: spread of repeated scores" panel is where to keep an eye on it.

## Tax and other adjustments in the total

The extraction check compared the line items with the total. A Malaysian
invoice with SST failed it: the items add up to the subtotal, not the total.
The extraction now reads `tax_amount` and `adjustments` (rounding, service
charge, delivery, discount), and the check compares items plus tax plus
adjustments with the total, within 1%.

After the deploy, a taxed invoice from Kestrel:

| | |
| --- | --- |
| Invoice | K-2026-202: items 120.00 + 190.00 = 310.00, SST 6% 18.60, total MYR 328.60 |
| Extraction | 96% confidence, no complaint about the totals |
| Risk | low (0.15) |
| Approval | auto approve, 99% sure (asked 3 times, all agreed) |
| Outcome | paid, transaction 11 |

The gap between items and total is 18.60, 5.7% of the total; the old check
allowed 1%, so it would have stopped this invoice as "line items don't add up".
The mismatch message now names what it counted:
"line items sum to 90.00 plus tax 5.40 but total is 120.00" (from the tests).

Kestrel's history went from 3 settled payments (average 347.33) to 4
(average 329.00) with K-2026-201, as the console showed.

## Names written in capitals

Phase 11a left one finding open: on the test suite's sample receipt, the name
"TAN CHAY YEE" was masked only as `CHAY`. spaCy recognised only part of a name
written in capitals. When it now finds a person on a line
that is nothing but a capitalised name (no company word such as SDN or BHD), it
masks the whole line. This is covered by the masking tests
(`test_a_name_in_capitals_is_masked_whole`) and not yet re-run live; the
receipt-picker's held-out SROIE receipts are the place to see it.
