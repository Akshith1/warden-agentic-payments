# Phase 7b live run: data quality (November 2026)

Phase 7b runs on the same Windows 11 machine, against the ledger and inbox
built up since phase 1: every payment from phases 1 to 7, the USAspending
reference vendors, and the SROIE and CORD receipts. Everything below comes
from the console and PowerShell; nothing is reconstructed.

## Setup

```
python infra/scripts/fill-secrets.py
Added from .env.example: PGPASS_WARDEN_QUALITY
Filled: PGPASS_WARDEN_QUALITY
```

After the init script created the read-only role, `warden-quality` reported
**healthy** about 6 seconds after it started, alongside every other service.

## First check: real data from every earlier phase

**Check now** as Amira at 4:39:15 PM: **14 passed, 1 failed, 0.5 s**, with
Great Expectations 1.24.1.

- **All five critical checks passed.** The ledger balances, every account
  matches its postings, cash is not overdrawn, and every Warden payment in
  vendor history is backed by a ledger payment of the same amount. That
  includes payments made before phase 3.5 changed the payment key's format.
- **One warning failed:** "Every loaded receipt has the labels the gate
  scores against", 1 row, id 34.

```
 id | source | external_key | split | ground_truth
 34 | sroie  | X51005433522 | train | {"entities": {"date": "10 MAR 2018", "total": "", "address": "...",
                                       "company": "UNIHAKKA INTERNATIONAL SDN BHD"}}
```

**Finding: a defect in the public dataset.** The SROIE label for this
receipt has an empty `total`. The receipt is in the train split, and the
evaluation gate scores the test split only, so no promotion was affected.
The check was right about the data but overstated the consequence. It now
covers the test split only, which is what the gate scores, and a test pins
the train-split case.

## A forged vendor history stops payments

Two settled payments let a vendor's invoice skip a person. To test that
rule, two history rows for Kestrel Print Works were written straight into
the database, as someone with database access could:

```sql
INSERT INTO historical_payments (vendor_id, amount, paid_on, source, external_ref, recorded_at)
SELECT id, 49.00, current_date, 'warden', 'FORGED-' || n, now()
FROM vendors, generate_series(1,2) n WHERE normalized_name = 'KESTREL PRINT WORKS';
```

Each row is valid on its own, so the database accepted both.

## Findings

1. **Dataset defect, wrongly weighted.** SROIE receipt `X51005433522` has
   an empty total label. It's in the train split, which the gate doesn't
   score. The check now looks at the test split only.
2. **Earlier phases left the ledger consistent.** Phase 3.5 changed the
   payment key's format, so a mismatch between history and ledger was
   possible; there is none.
3. **Still open: the data catalogue (OpenMetadata).** It is the second half
   of 7b, and depends on the memory Docker Desktop can give it.
