# Phase 11b live run: the write-once audit copy (November 2026)

The same Azure deployment as [phase 11a](2026-11-phase-11a.md), redeployed with
`.\infra\azure\deploy.ps1` after phase 11b-1 merged: a storage account with an
`audit` container under a time-based immutability policy (one day, protected
append writes, unlocked), and the control plane copying every audit entry to
it with its own managed identity. It worked on the first deploy. Everything
below is copied from PowerShell and the console.

## The copy catches up

The audit log already held 25 entries from the phase 11a runs. A few seconds
after the new control plane started, the console's **Audit log** page showed
two green notes:

> **Chain verified.** 25 entries, each sealed with the fingerprint of the one
> before. Latest fingerprint `4d375923f8251dec`.
>
> **Matches the write-once copy.** Entries 1 to 25 are also kept in Azure Blob
> storage, where nobody can change or delete them, and every one matches this log.

Entries written before the copy existed were copied too: where the copy had
got to is read from the copy itself, which was empty, so it started at entry 1.

## Scenario 28: a rewritten history

The insider: someone with the control plane's database, who rewrites an entry
and then recomputes every fingerprint after it, so the chain verifies again.

```
> az containerapp exec -n warden-control -g warden-rg --command "python -m app.tamper --seq 3 --rechain"
INFO: Successfully connected to container: 'warden-control'. [ Revision: 'warden-control--0000004', ... ]
Direct UPDATE refused by the trigger: the audit log is append-only
Switched off the trigger and rewrote entry 3 (run_step):
  before: {"amount": null, "at": "2026-11-04T19:04:35.802602+00:00", "model_category": "none", ...
  after:  {"amount": null, "at": "2026-11-04T19:04:35.802602+00:00", "model_category": "none", ...
Recomputed the fingerprints of entries 3 onwards: the chain will verify.
```

Entry 3 was the guardrail step of the first run; with no "approve" to turn
into "reject", the script added `"edited": true` at the end of its payload,
past the 150 characters it prints, so the two lines look alike.

The Audit log page, refreshed:

> **Chain verified.** 25 entries, each sealed with the fingerprint of the one
> before. Latest fingerprint `363adc5cf1c9d99c`.
>
> **This log no longer matches its write-once copy:** entry 3 differs from the
> write-once copy (payload, hash). The copy in Blob storage can't have
> changed, so the database has been altered from entry 3 on, even if its chain
> verifies.

Entries 3 to 25 were marked. The chain alone was fooled, as designed: every
fingerprint was consistent again. The only trace in the chain was the new
latest fingerprint, which someone would have had to write down beforehand;
the write-once copy made that comparison for every entry.

## What this run proved

- The control plane wrote to Blob storage with its managed identity; the
  storage account takes no keys, and no other identity has access to the
  container.
- The copy picked up existing history and kept up with new entries.
- A careful rewrite of the database, the case the hash chain can't catch, was
  caught at the first changed entry.

The Azure audit database stays altered after this run (the red note stays);
`teardown.ps1` and a fresh deploy start it clean.

# Phase 11b-2: API Management for outside systems

API Management (Consumption) in front of the backend, with an "Invoice intake"
product, and a "Warden intake" app registration standing in for an outside
system: it signs in as itself with the submitter role only.

## Finding: a quota can only be set on a product

The first deploy stopped at the foundations:

```
"target":"quota","message":"Error in element 'quota' on line 9, column 6: Policy is not allowed in the specified scope"
```

The rate limit and daily quota had been put in the API's policy; API
Management accepts `quota` only on a product. Both limits moved to the Invoice
intake product's policy ([`apim-product-policy.xml`](../../infra/azure/apim-product-policy.xml)),
which runs before the API's token check. The Entra ID part of the deploy had
already finished and was skipped on the rerun.

## Playing the outside system

`.\infra\azure\try-api.ps1`, after the redeploy:

```
Gateway: https://warden-apim-<suffix>.azure-api.net/warden
Signed in as the Warden intake app (1b281bff-…); first calls may wait while Warden wakes.

1. No subscription key                       401  as expected
2. A key but no token                        401  as expected
3. A token, straight to the backend          403  as expected
4. Key and token, through the gateway        202  as expected   {"run_id":"9a5f919f-…","status":"submitted"}
                                             invoice K-2026-155258, run 9a5f919f-…
5. The run, through the gateway              pending_human  (limited history: 1 prior payment(s), auto-approval needs 2)
6. A burst of 12 requests                    429 from call 8 of 12, as expected   (404 404 404 404 404 404 404 429 429 429 429 429)
```

Check 3 is the one that matters most: a valid token for Warden, sent straight
to the backend's public address, was refused because it didn't come through a
front door. The burst hit the limit of 10 calls a minute at call 8, because
checks 2, 4 and 5 had already counted (the product's policy runs before the
token check, so even the tokenless call counted). On the first run of the
script, step 5 printed nothing: the script read the run's status from the
wrong place in the API's answer, fixed in the script.

## The run, decided in the console

Both runs the intake app submitted (K-2026-154813 and K-2026-155258, MYR
210.00 each, Kestrel) waited for a person, and Rajesh approved them. The
four-eyes rule that had refused his own invoices allowed these, because an
outside system submitted them: the policy engine "Allowed for
guptha.rh@gmail.com (approvers-may-approve, controllers-may-approve-any-amount)".
They posted as transactions 6 and 7, after the dry run and the 20-second hold.

## Finding: masking took an invoice number for a phone number

The trail's first step for the API's invoice read "2 phone number, 1 person";
there was one phone number and no person. Reproduced from the same text: the
invoice number `K-2026-155258` has a phone number's digits, and with Windows
line endings (the script runs in PowerShell) spaCy read "Bill" of "Bill To:" as
a name. Neither changed the outcome, since the real values go back after the
models answer, but a model shown `Invoice No: <PHONE_NUMBER_2>` has less to
work with. Fixed in [`warden-pii/app/masking.py`](../../warden-pii/app/masking.py):
a number after a document label (invoice, receipt, ref, order, PO…) is not a
phone number, and line endings are normalised before the text is analysed. The
same text with Windows line endings is now a test.

## What 11b-2 proved

- An outside system can submit invoices only through API Management, with a
  subscription key and an Entra ID token holding the submitter role, within a
  rate limit; the backend refuses a valid token that skipped the gateway.
- An app's submissions go through the same agents, policy and four-eyes rule
  as a person's, and the audit log records how each came in.
