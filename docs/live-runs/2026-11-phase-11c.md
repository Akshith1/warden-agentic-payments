# Phase 11c live run: data, data quality and monitoring on Azure (November 2026)

The same Azure deployment, redeployed with `.\infra\azure\deploy.ps1` after
phase 11c: the data loader as a one-off job, the data-quality service with a
read-only login and a schedule, and monitoring in Application Insights with a
workbook in place of the Grafana dashboard. Everything below is copied from
PowerShell, the console and the Azure portal.

## Finding: the data loader ran out of memory

The first deploy stopped at the loader:

```
== Loading receipts and vendor history (the warden-data-loader job: 5-15 minutes)
  Running
  Failed
```

Its console log held one harmless line; Azure's system log for the job said why:

```
Started container 'data-loader'                                                    22:56:36
Container 'data-loader' was terminated with exit code '137' and reason 'ProcessExited'   22:56:55
Job has reached the specified backoff limit
```

Exit 137 is the kernel killing the process: it had used up the job's 2 GB in
twenty seconds. The loader streams the SROIE and CORD datasets and casts the
image column to `decode=False`, so it never decodes an image, but the Parquet
reader still read every image's bytes, a row group at a time. Locally Docker
gives it far more memory, so it never showed.

**Fixed** in [`warden-data-loader/loader/invoices.py`](../../warden-data-loader/loader/invoices.py):
the reader is asked for only the columns used (SROIE: key, words, entities;
CORD: ground_truth), so the images are never read. On a 1 GB test file with
5 MB "images", peak memory went from 4,654 MB to 154 MB. The job also got 2 CPUs
and 4 GB as headroom. The next deploy:

```
== Loading receipts and vendor history (the warden-data-loader job: 5-15 minutes)
  Running
  Succeeded
```

## Monitoring

The **Warden** workbook in the resource group, over the last 24 hours:

- Runs by outcome: 1 pending_human; why runs went to a person: first_seen.
- Time per graph step: risk scoring 3.83 s, guardrail 1.79 s, extraction 1.45 s, privacy 0.33 s.
- Model tokens by agent: extraction about 1,940, guardrail and risk scoring about 1,190 each.
- Risk scores: one, 0.2, on the routine route.
- Requests each service served: backend 460, control 394, quality 9 (309 ms average,
  cold starts), policy 5 (602 ms), ledger 3.
- Calls between services, including the ledger's Postgres calls at 2.9 ms.
- Failed requests: one, `POST /runs/{run_id}/resume` 403: the refused self-approval.
- The backend's step log: the OJC run's four steps, 5:26:01 to 5:26:08 PM.

Two panels failed at first, both in the workbook's queries: "Model tokens by
agent" did not parse (`kind` is a reserved word in KQL), and "The backend's step
log" was empty (Azure Monitor names services with their namespace,
`warden.warden-backend`). Fixed, and fine on the next look. "Calls between
services" also listed `GET /status http send` and the like, hundreds of them:
the ASGI instrumentation's own spans around each response, which the backend
switches off in code but `opentelemetry-instrument` offers no setting for. The
query now leaves those out (`type != "InProc"`).

**Application map** in warden-insights drew the architecture from live data:
the backend calling policy, control and the ledger; policy calling the ledger
and control; quality calling control; the ledger calling Postgres
(`warden-pg-…`, 2.9 ms over 20 calls). `localhost:12356` is Container Apps'
managed identity endpoint: the backend and policy service getting the Entra ID
tokens they show the ledger. `warden-*` stands for the gateway, masking and OCR,
which aren't instrumented.
