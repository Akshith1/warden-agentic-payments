# Phase 9b live run: observability and agent consistency (November 2026)

Phase 9b runs on the same Windows 11 machine, with real models. Grafana's
all-in-one image (`grafana/otel-lgtm` 0.38.1) receives traces, metrics and
the step log from the backend, ledger, policy, control plane and data-quality
services. Everything below comes from Grafana, the console and PowerShell;
nothing is reconstructed.

## A run as one trace

Invoice `K-2026-004` (Kestrel Print Works, MYR 27.00). In Grafana Explore
(Tempo), the run segment `invoice run (submit)` was one trace of **45 spans
over 10.66 s**:

| Step | Time | Inside it |
| --- | --- | --- |
| privacy | 276 ms | The call to `warden-pii`, timed from the backend; the PII service itself stays off the telemetry path on its internal network |
| guardrail | **2.02 s** | `chat warden-guardrail`, the slowest step |
| extraction | 1.26 s | `chat warden-routine` |
| risk_scoring | 1.46 s | `warden-ledger`'s `GET /vendors/lookup` and its three SQL `SELECT`s, in the same trace |
| between steps | 5 to 8 ms | `warden-control`'s `POST /events`, the audit-log write |

The `step risk_scoring` span carried `warden.risk_score` 0.1,
`warden.risk_level` low, `warden.route` warden-routine,
`warden.vendor_known` True and `warden.run_id`. **Related logs** on the span
links to the matching step-log lines in Loki.

## Finding 1: counts read 0

The first dashboard showed `pending_human` 0 and `settled` 0 after two runs,
with the right labels and empty latency graphs. Prometheus took each
counter's first reading as its baseline, so anything counted before the first
export never showed as an increase. **Fix (PR #27):** Prometheus 3.15.1's
`created-timestamp-zero-ingestion`, which stores a zero at the start time
OpenTelemetry sends with each cumulative point (checked in Prometheus's
source to cover OTLP).

## Finding 2: the risk agent wasn't consistent

The phase 7 live run scored two Kestrel invoices 0.60 and 0.15.
`python -m app.consistency RUN_ID` asks the agents the same question again
with exactly the evidence a run sent them.

| Run | Setting | Risk scores | Spread | Levels |
| --- | --- | --- | --- | --- |
| K-2026-004 | provider default | 0.15, 0.15, 0.15, 0.10, 0.20 | 0.10 | low ×5 |
| K-2026-004 | provider default | 0.10, 0.15, 0.15, 0.10, 0.15 | 0.05 | low ×5 |
| **K-2026-002** | provider default | 0.46, 0.78, 0.85, 0.78, 0.66 | **0.39** | medium, high, high, high, medium |
| K-2026-002 | `risk-scoring=0` | 0.85, 0.85, 0.78, 0.78, 0.78, 0.78, 0.85, 0.78, 0.78, 0.85 | 0.07 | high ×10 |
| K-2026-002 | `risk-scoring=0` | 0.78, 0.85, 0.78, 0.78, 0.85, 0.78, 0.85, 0.78, 0.75, 0.78 | 0.10 | high ×10 |

- **Most of the 0.60 vs 0.15 difference is the evidence.** K-2026-002 was
  twice the vendor's only previous payment (90.00 against 45.00); K-2026-004
  came with more history and a smaller amount.
- **On borderline evidence, the model's own variation was large.** The same
  question got 0.46 to 0.85, flipping between medium and high, and "high
  risk" is itself an escalation reason.
- **Temperature 0 on the risk agent (PR #28)** brought the spread to 0.07 to
  0.10 and the level to high every time. The run's original 0.60 was a low
  draw.

## Finding 3: the approval agent was a coin toss on the same evidence

With the risk agent fixed, ten repeats of the approval agent on K-2026-002's
evidence answered **escalate 6, auto_approve 4** (earlier, 5 of 5 escalate:
about an 8% chance at that rate).

Its route is OpenAI's reasoning model, which accepts only temperature 1 while
reasoning. The gateway's `drop_params: true` would have discarded
`approval=0` silently while the trace still showed it requested; checked
against LiteLLM 1.106.5 before it was tried.

**Fix (PR #29):** an auto-approval must be unanimous across three asks.
Escalate and reject stand on the first answer; an auto_approve is asked again
until three agree, else a person decides, and the lowest confidence is the one
checked against the threshold. Measured on the same run:

```
Approval agent: escalate ×10; confidence 0.78 to 0.93.
  Rule: an auto-approval needs 3 of 3 asks to agree. The model was asked 11 times in all;
  1 answers said auto_approve.
  The decisions all agree.
```

One first answer said auto_approve; the second ask said escalate, so a person
decides. The raw rate was 1 in 10 this time against 4 in 10 an hour earlier,
on identical evidence: the reason to rely on a rule rather than one sample.

**No money was at risk at any point.** K-2026-002 never reached the approval
agent in its real run: the code rule (two settled payments before
auto-approval) and the same rule in Cedar sent it to a person after the risk
step. The variation matters for vendors that pass those rules.

## Findings

1. **A counter's first value is lost without a start time** (fixed, above).
2. **The risk agent varies on borderline evidence**; temperature 0 fixes it.
3. **The approval agent varies, and its model ignores temperature**; agreement
   across asks fixes it.
4. **A gateway that silently drops parameters can make a fix look applied.**
   Settings that change model behaviour are measured, not assumed.
5. **The guardrail's model call is the slowest step** (2.02 s of 10.66 s).
   A candidate for a smaller model or caching, now that it's measured.
