# Phase 11a live run: the core payment path on Azure (November 2026)

A personal Azure subscription on the free account ($200 credit), region Central
US, deployed from the same Windows 11 machine with `.\infra\azure\deploy.ps1`
(Azure CLI 2.92, Docker Desktop, Windows PowerShell). The templates and
scripts had been checked here only against stand-ins for `az` and `docker` and
a Postgres set up to resemble Azure's; this was their first run against Azure.
Everything below is copied from PowerShell and the console.

## The first deploy

One run of the script, about 30 minutes end to end: the six resource providers
registered, Entra ID set up (the "Warden" and "Warden ledger" app
registrations, the console's client secret, the test people `amira` and
`clerk`), the foundations deployed with Bicep, eight images built and pushed to

## Finding 1: the backend couldn't create its tables

Submitting the first invoice ended in **HTTP 504**. The backend's log:

```
File "/srv/app/main.py", line 58, in lifespan
    checkpointer.setup()
psycopg.errors.InsufficientPrivilege: permission denied for schema public at character 28
ERROR:    Application startup failed. Exiting.
```

On Azure Database for PostgreSQL Flexible Server, the `public` schema of a new
database belongs to `azure_pg_admin`, not to the database's owner, so a
service that owns its database still can't create tables in it. Standard
Postgres, which the database job had been tested against, gives the schema to
the database's owner. **Fixed** in the database job: each service is made the
owner of its database's `public` schema
([`infra/azure/db-init.sh`](../../infra/azure/db-init.sh)). CI's Azure check now
sets up its Postgres the way Flexible Server does (`public` owned by
`azure_pg_admin`) and checks that all three services can create a table. After
a redeploy (about five minutes, every image from cache), the backend started.

## Finding 2: masking garbled the invoice's item table

The next two runs stopped at extraction:

> additional documentation requested: line items sum to 454.00 but total is 622.00

The extraction agent had listed two of the three line items. The run page's
**What the models saw** showed why: personal-data masking had rewritten the
item table before any model saw it.

```
No. 12, Jalan Perindustrian 3, 47500 <PERSON_1>, Selangor
Tel: <PHONE_NUMBER_1>
Bill To: <PERSON_2>.
A4 <PERSON_3> (box of 5)        4        42.00        <PHONE_NUMBER_2>
Printer <PERSON_4>           2       185.00        370.00
```

spaCy's small model took "Copier Paper", "Toner Cartridge" and the town
"Subang Jaya" for people; Presidio took the amount `168.00` for a phone
number; the "Bill To:" label rule took the company "Warden Demo Co." for a
name. With that line's amount hidden, the extraction agent left the line out,
and the line-item check stopped the run, as it should. The failure was safe:
nothing was paid on a wrong reading. It is a phase 7 finding, and it affects
the local stack too.

**Fixed** in [`warden-pii/app/masking.py`](../../warden-pii/app/masking.py):
an amount is never a phone number (nor anything with fewer than seven digits);
a name spaCy guessed on a line ending in an amount (an item row) or on a line
with a postcode (an address) is ignored; a labelled name ending in a company
word (Co, Sdn Bhd, Ltd…) is a business; and a labelled name stops at a wide gap
or the end of the line (it used to run on: "Lim Mei Ling   Total"). Names after
a label ("Cashier:", "Attn:") are still masked wherever they are. The same
invoice is now a test. After the fix, the trail's first step read "Replaced
before any model saw the text: 1 phone number", and the table reached the
models intact.

Still open: on the sample receipt the test suite has always used, the name
"TAN CHAY YEE" is masked only as `CHAY`. That was already so before this fix.
A larger spaCy model, or a recognizer for names in capitals at the top of a
receipt, would be the next step.

The first invoice used in this run also carried 6% SST (sales tax) between
subtotal and total. The line-item check compares the items with the total and
has no notion of tax, so it would stop any taxed invoice. That too is a
finding for a later phase; the remaining runs used an untaxed invoice.

## The payment path

K-2026-104, Kestrel Office Supplies, MYR 622.00, submitted as Rajesh:

| Step | Result |
| --- | --- |
| Personal data masked | 1 phone number |
| Guardrail | no instructions to the AI, by the rules or the safety model |
| Extraction | three line items, 96% confidence, bundled prompt (no MLflow on Azure yet) |
| Risk | medium (0.42), sent to a person: first-seen vendor. "Never paid before" was read from the ledger with the backend's managed identity |

| Policy engine | allowed for amira@…onmicrosoft.com (approvers-may-approve) |
| Ledger dry run | would balance; nothing written |
| Settlement hold | 20 s |
| Ledger commit | posted as transaction 3, written with the backend's managed identity |

## What this run proved

- One script deploys the core path to Container Apps from a Windows PC, and
  running it again changes only what differs (the redeploys took about five
  minutes).
- People sign in with Entra ID; roles come from app roles; only people given a
  role can sign in at all; the four-eyes rule and the role tiers hold exactly
  as with Keycloak.
- The ledger took writes from the backend's managed identity, and reads from
  the backend's, with no key: the phase 6b design without SPIRE.
- Every app scaled to zero between steps of the test and woke on demand; the
  first submit after a quiet spell took about a minute.
- Secrets came from Key Vault; none is in any app's settings.
