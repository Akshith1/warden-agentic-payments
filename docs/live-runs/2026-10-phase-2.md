**Finding: the gate was too lenient.** The casual prompt got the vendor wrong
on 16 of 40 receipts and still passed, because date and total are easy for
both prompts and the average hid the one field that links an invoice to its
vendor's payment history (the phase 1 OJC problem). The gate now also requires
`FIELD_FLOOR` (0.75) on every field. That number was chosen after seeing this
run; with these figures the casual prompt would be BLOCKED on vendor 0.60. The
next gate run will show whether it holds.

## Promotion gate, second run: stopped by the provider

The rerun with the per-field floor hit Groq's free-tier daily limit partway
through the casual candidate:

```
Rate limit reached for model `openai/gpt-oss-120b` ... on tokens per day (TPD):
Limit 200000, Used 198841, Requested 1543. Please try again in 2m45.888s.
  [casual] 27/40 X51005442343 {'vendor': False, 'date': False, 'total': False} ERROR InstructorRetryException: Error code: 429 ...
```

**Finding: the gate scored a refused call as three wrong fields.** That would
have blocked the casual prompt for the wrong reason, which is false evidence
from a governance control. The gate now distinguishes the two failures: a model
that never produces a valid `InvoiceExtraction` after retries is a real miss;
a provider refusal (429, 5xx, timeout) stops the gate as INCONCLUSIVE, with
nothing registered and `production` unchanged. The run above predates that fix;
its result is discarded, not recorded.

## Promotion gate, third run: the per-field floor blocks a prompt

The next day, after the daily limit reset, with `EVAL_SAMPLE_SIZE=20` to stay
inside the free-tier budget:

```
Promotion gate: 20 held-out SROIE receipts, overall threshold 0.80, per-field floor 0.75, route warden-routine
...
candidate     accuracy  vendor  date   total  errors  verdict      registry version     why
structured       0.900    0.75   1.00   0.95       0  PROMOTED     warden-extraction v3     -
casual           0.833    0.50   1.00   1.00       0  BLOCKED      warden-extraction v4     vendor 0.50 < floor 0.75

`production` -> structured. Restart warden-backend to load it.
```

The casual prompt would have passed the first run's average-only rule (0.833
is above 0.80). The floor blocked it on the field that matters: it misnamed the
vendor on 10 of 20 receipts. This is scenario 05 (a worse prompt is really
blocked), shown live, with the reason recorded in the registry.

**Open item, not hidden:** the promoted structured prompt reached vendor
accuracy 0.75 exactly, on the floor itself (5 of these 20 receipts wrong; 0.82
on the earlier 40). It passes, but with no margin. The next step is a better
vendor extraction prompt scored by the same gate, not a lower floor.
