# Phase 3 and 3.5 live run (November 2026)

The console (phase 3) and vendor aliases (phase 3.5) run on the same Windows 11
machine as the earlier phases, with real models and the prompt promoted in
phase 2 (`warden-extraction` v3). Everything below comes from the console;
nothing is reconstructed.

## Phase 3: a known shop looked first-seen

A SROIE receipt from OJC Marketing was submitted from the console's inbox.

| Field | Value |
| --- | --- |
| Extracted vendor | `TAN CHAY YEE OJC MARKETING SDN BHD` |
| Vendor already in the ledger (phase 1) | `TAN CHAY YEE *** COPY *** OJC MARKETING SDN BHD` |
| Amount | 170.00 |
| Escalation | first-seen vendor |
| Outcome | approved by a person in the console, settled on Nov 1 |

Prompt v3 dropped the `*** COPY ***` stamp but still kept the cashier's name,
so the name did not match the vendor paid in phase 1, and the ledger treated
a shop it had paid before as one it had never paid. The trail also showed the
wait for the human as `+1055 s`, which led to the console showing long waits
in minutes and hours.

**Finding.** Vendor names read from receipts vary from document to document.
The gate's vendor accuracy (0.75, exactly on the floor) says the same.
Matching names "loosely" would fix the symptom but opens a known fraud path
(look-alike vendor names), so phase 3.5 lets a person confirm the link instead.

## Findings and what changed

1. **Two vendors for one shop remain.** The phase 3 approval saved
   `TAN CHAY YEE OJC MARKETING SDN BHD` as a vendor of its own before aliases
   existed. An alias joins a *new* name to an existing vendor; merging two
   existing vendors is refused by design and would need its own reviewed
   feature.
2. **Console polish** from the screenshots: the whole row in Runs opens the
   run (only the vendor name did); provider errors in the list are cut to one
   line with the full text on the run page; "1 settled payment" is singular.
